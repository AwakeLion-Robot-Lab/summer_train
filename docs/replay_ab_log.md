# 回放 A/B 记录

从 `config/auto_aim.yaml` 的注释里挪出来的回放测量，配置文件里只留结论。除非另注，判据一律是
`track_diag` 的 `pred_px`（开环 100 ms 预测的像素误差），录像是 `records/` 下的八段 3 m 录像。

重新做 A/B 之前先看 `track_diag` 的输出是否逐次确定：L2 推理偶有末位抖动，同一个二进制两次运行的
`obs.csv` 可能不同，结论只能拿 `obs.csv` 相同的运行对来下。

## 推理线程数（`inference.num_threads`）

单帧推理耗时（ms）：默认 10.49 / 8 线程 + P 核 10.34 / 8 线程 + E 核 10.61 / 4 线程 13.86。
差别都在噪声里，只有线程数少到 4 才明显变慢。除非换了模型或换了机器，保持默认即可。

## 角点精修（`refiner`），2026-09-19

### `color_channel_diff` 从 false 改成 true（灰度 → 差分）

```text
长度噪声 8/8 下降 12~47%      pred p50 7/8 改善
长度偏差 7/8 改善，低曝光段基本消失（fast_run −1.86→−0.09，fast_stop −1.78→+0.07）
唯一回退是 fast_stop 的 ≤20px 58.2%→53.2%，但那段 p50 就卡在 19.5 px
的门槛上，同一段的 p90 是改善的（24.91→24.66）。
```

为什么灰度是错的：灯条过曝后核心 B=R=255，灰度阈值切到的是这个饱和白核，而白核的大小完全由曝光决定——
这正是长度偏差随曝光变化的原因（过曝段 −0.9、低曝光段 −1.8）。差分图里白核归零，切到的是灯条彩色边缘，
更接近真实发光边界。实测 gray>240 的像素里 B−R 中位数为 0，而灯条边缘仍有 70~90。

### 同一轮里查清的另外三件事

1. **差分带来的"改善"绝大部分是精修不再触发了，不是修得更准。** 触发率 3m_high 31.8%→0.36%、
   3m_mid 59.5%→4.3%、fast_stop 79.1%→11.2%。把"直接关掉精修"当第三个对照拉进来（`enable: false`，
   与 `max_endpoint_distance_px=2.0` 那轮逐位相同，可互相印证）：

   ```text
   长度噪声  关 / 差分 / 灰度
   3m_high  1.374 / 1.408 / 1.962      3m_low  0.992 / 1.254 / 2.304
   3m_mid   0.957 / 1.195 / 2.204      fast_stop 0.987 / 1.310 / 2.830
   ```

   pred p50 三者在 ±2% 内打平，长度噪声上 4/4 都是关掉最好。**结论：精修在现有八段上、在试过的每一种
   配置下都是净负的。** 留着 `enable: true` 的唯一理由是它最该起作用的 5 m 工况还没有录像；真要凭现有
   证据决定，就该关掉。

   差分图上精修失效的机理（成因分解，见 `RefineStats`）：3m_high 差分保留网络 3626 中没找到灯条 3257
   （89.8%），不是门限拦下了坏建议，是传统检测压根没凑够两根灯条。再往下拆到轮廓级：

   ```text
   thr  轮廓  过筛  毙于角度/长宽比/长度      触发率
   10   5553    5     401 / 5048 /  99         0%
   20   8081  228     649 / 6732 / 472         0%
   30   7354  521     429 / 6112 / 292         0%
   50   8002 1438     485 / 5862 / 217         0.36%
   ```

   每一档都是长宽比毙掉七到九成，而且阈值**越低越糟**（10 只剩 5 个轮廓过筛）。所以别再去调
   `color_diff_threshold` 了，那不是瓶颈。真正的原因：过曝灯条在差分图里核心归零、只剩左右两道彩色窄边，
   `findContours` 拿到的是两条细长条而不是一根灯条，短/长远低于 `min_ratio` 0.08——要救得先做形态学闭运算
   把两道边合回去，或者重定 `min_ratio`/`max_ratio`，不是动阈值。
2. `pca_corner_correction` 关掉能砍掉约一半长度偏差（−1.11→−0.69），说明 `correctLightbarEndpoints` 取的
   是跳变内侧那一格亮点而非边沿，每端内缩约 0.5~1 px。但它不改善噪声，改差分之后这个残留偏差也大幅缩小了。
3. 噪声不是逐帧切换造成的：把 `max_endpoint_distance_px` 推到 1000（无条件替换）噪声炸到 7.76、pred p50
   从 1.72 升到 8.22。这个门限是在限制损害。

### `light_finder.color_channel_diff`

差分会把灯条产出量砍掉一大截，过曝录像上尤其狠：3m_mid 5364 -> 1679、3m_run_mid 5093 -> 1409、
3m_run_fast 3981 -> 1643；剩下的还进不了关联——3m_mid 和 3m_run_no 开差分之后的预测误差与
"侧边灯条整个关掉"逐位相同。机制与 refiner 那边同一个：过曝灯条核心 R≈G≈B，差分把白核归零后只剩
两条细边，`min_ratio` 0.08 会把它们毙掉。八段里 false 赢六段。

## 端点观测噪声（`ieskf.sigma_*`），2026-09-19

每个端点的像素 sigma 沿灯条与垂直灯条分开给：`sigma = max(sigma_min_px, 系数 × 灯条像素长度)`，上下
端点互相独立。当前取 rmcs_auto_aim_v2 的常数 R = 40 px²（两个系数为 0）；录像都在 3 m，按长度缩放在
别的距离上是否更好还没比过。三次扫描：

1. **尺度**（3m_high，pred p50 / p90 px）：

   ```text
   1.5  →  3.19 / 6.49      3.0  →  2.27 / 4.42
   6.32 →  1.72 / 3.38     12.0 →  1.52 / 3.08     25.0 → 1.83 / 3.92
   ```

   最优在 12 附近，但 6.32→12 只换 12%，而 1.5→6.32 是 46%：已在平台区，继续抠这个数收益很小。
   12 这个点没在激进录像上复查过，别直接搬。
2. **NIS 在这个系统上不是可优化目标。** 它随 sigma 减小单调趋近 1（1.5 时 0.62，6.32 时 0.048），
   方向与 pred_px 完全相反。原因是 NIS 的一致性判据假设观测噪声是白的，而我们的不是：`light_noise`
   去趋势量到的白噪声只有 1.18 px，剩下的是慢变相关误差和那个长度偏差。大 R 在这里实际起低通作用，
   压的就是它们。所以 6.32 远大于 1.18 不是配错了。
3. **两端点相关**（曾经的 `rho_along` / `rho_perp`，已回退）：物理上成立——细亮斑横向整体平移，上下
   端点同向。但实测不划算，`rho_perp` / pred p50（high / run_fast）：

   ```text
   0.0 → 1.718 / 3.600     0.4 → 1.667 / 3.721
   0.8 → 1.718 / 3.832     0.8 且 rho_along=-0.2 → 1.712 / 3.885
   ```

   静止段最多 -3%，机动段单调变差（p90 +7%，≤20px 命中率 96.0%→95.0%）。形状比尺度次要一个量级。
   这条推理链很容易重新长出来，别再推一遍。

## 侧边灯条剖面搜索（`light_finder.search: profile`），2026-09-24

`contour` 是在 light_roi 里盲检再关联；`profile` 拿 L3 预测的每根侧边灯条（`lightSlots` 那几个槽位）
逐行取垂直剖面找脊线。两者都开 `ieskf.enable_lights_measure: true`，off 是仓库里的现值（false）。
每臂各跑两次，同臂两次结果逐位相同（3m_run_fast 的 contour 除外，第 6 位小数抖）。

先查的一件事：**现有 contour 路径在当前代码上几乎等于关着。** 3m_high 上 3766 根候选、L3 采纳 0 根，
pred 与 off 逐位相同；3m_run_fast 采纳 1 根、3m_run_mid 3 根。候选中心离预测槽位的距离 p50 为 89 px，
1575 个 (灯条, 槽位) 对里只有 5 个在半个灯长以内——它找到的是别处的亮条，不是预测位置上的侧边灯条。
9-19 那一节"侧边灯条帮了五段"的数字是当时的代码，不适用于现在。

p90 八段里七段改善，静止段的尾巴砍得最多（3m_mid -42%）；p50 三段改善、五段变差，静止段变差最多。
与 9-19 "侧边灯条在静止段是负收益"的方向一致：多塞的观测在已经亚像素的静止段上是噪声，但能压住
偶发的大误差。fast_* 两段的 17~20 px 不是侧边灯条能解决的量级，改动在噪声里。

实现上踩过的坑（都在 3m_high 第 140 帧上看出来的，那帧右侧是一块网络漏检、几乎侧对相机的板）：

1. 底图取目标通道（B）：灯条背后的白海报 B 同样饱和，半高区铺到剖面边缘，灯条只剩下端一小截。
2. 底图取 B−R：过曝白核被挖空（与 refiner 那节同一个机理）。最后用的是"目标通道与 G 都 ≥ 245 取 255，
   否则 0.5×(B−R)"：白核 G 在 249~255，海报 G 在 229~240，G 是分开两者的那个通道；乘 0.5 是因为贴车身
   一侧的光晕 B−R 能到 180~215，和白核同档的话半高区同样铺到边上。
3. 取全局最亮段会跳到旁边的海报上，改为取离预测轴线最近的一段；直线拟合逐个剔掉最差行（海报行）。

找到的灯条比预测长 13%（中位数，光晕），角度差中位数 0.03 rad。**这个长度偏差是 p50 在静止段变差的
头号嫌疑**，下一步先试把端点门槛从半高提到 0.6~0.7，看长度比能否回到 1.0、静止段 p50 能否回来。
在那之前仓库默认仍是 `search: contour` 且侧边灯条观测关着。
