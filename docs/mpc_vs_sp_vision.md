# 本项目的 MPC 与 sp_vision 的逐条差异

对照对象：`sp_vision_25-main/tasks/auto_aim/planner/`（`planner.cpp` /
`planner.hpp` / 内嵌的 `tinympc/`）。记录时间 2026-09-12，对应本分支
`plan/mpc` 的 `l4_planning/mpc.*` 与 `l4_planning/armor/planner.cpp`。

本项目的 MPC 是照着 sp 搬的，所以默认"一致"，本文只记**不一致的地方**以及
每一处的依据。想看四套开源各自怎么处理切板，见
`armor_switch_and_mpc_survey.md`。

## 一、完全同构的部分

| 项 | 双方共同的值 |
| --- | --- |
| 模型 | `x = [角, 角速度]`，`u = 角加速度`，`A = [[1,dt],[0,1]]`，`B = [0,dt]`，仿射项 `f = 0` |
| 权重 | `Q = [9e6, 0]`、`R = 1`——只罚位置偏差，不罚速度偏差 |
| 窗口 | `DT = 10 ms × HORIZON = 100`，中心落在命中时刻，读 `HALF_HORIZON = 50` |
| 参考坐标 | 都减去 `yaw0`（命中时刻的瞄准角）存相对量 |
| `x0` | 都取参考轨迹首列，**不是云台实测姿态**——开环，闭环留给下位机 |
| 每个采样点 | 都重新选板、重新解一次弹道 pitch；飞行时间整窗只解一次 |
| 约束 | 只有 `|u| <= a_max`，状态界形同虚设（sp 设 ±1e17） |
| adaptive_rho | 双方都不开（TinyMPC 默认 0，sp 没打开） |

## 二、六处有意偏离

### 1. rho 与迭代次数：1.0 / 10 → 10.0 / 25

sp 在 `setup_yaw_solver` 里写死 `tiny_setup(..., rho = 1.0, ...)`，
`settings->max_iter = 10`。

拿 `records/3m_run_fast` 里导出的 50 条真实参考，对照稠密 QP 的精确解量中点
偏差（单位：度）：

| rho \ 迭代 | 10 | 25 | 50 | 100 |
| --- | --- | --- | --- | --- |
| 1（sp 的值） | 3.698 | 1.736 | 0.352 | 0.015 |
| **10** | 0.517 | **0.025** | 0.002 | 0.000 |
| 100 | 0.699 | 0.445 | 0.236 | 0.087 |
| 1000 | 1.868 | 1.276 | 0.921 | 0.682 |

而精确解本身只偏离参考 0.1 度量级（中位 0.073 度、p90 1.26 度、最大 2.40 度）。
所以 rho=1 / 迭代 10 那 3.7 度**全是没收敛出来的假象**，实机表现是命令单帧
甩出十几度再弹回。双轴合计 25 次迭代约 63 us/帧，10 次约 27 us/帧。

### 2. 参考速度：无条件中心差分 → 只在同板采样点之间差分

sp 的 `get_trajectory` 对整条窗口无条件做中心差分：

```cpp
auto yaw_vel = tools::limit_rad(yaw_pitch_next(0) - yaw_pitch_last(0)) / (2 * DT);
```

跨过切板时，这个差分把整块板宽度的台阶除以 `2*dt`：3 m 处两块板的方位角差约
5.3 度，dt=10 ms 下得到 **4.6 rad/s 的假速度**。本项目改成只在同一块板的采样
点之间差分，前后都换板时报 0。

位置上的台阶必须保留——那才是切板本身，正是要交给 MPC 去平滑的东西。

**那 sp 为什么没事？因为 `q_velocity = 0`。** 速度那一行的线性代价
`q_.row(1) = -q_velocity * x_ref.row(1)` 恒等于零，窗口中间那些列的速度参考
根本不进代价。在同样 50 条参考上量（把第 1..N-2 列全换成 sp 的无条件中心差分）：

| 假速度落在哪 | 中点命令挪动（度，中位 / p90 / 最大） |
| --- | --- |
| 中间列（1..N-2） | 0 / 0 / 0——逐位相同 |
| 末列（经 Pinf 进终端代价） | 3.0e-6 / 7.0e-6 / 8.2e-6 |
| **首列** | **35.12 / 38.27 / 38.78** |

100 列里有 99 列怎么差分都无所谓，**唯独第 0 列不行——它不是代价项，它是
`x0`，整条滚动轨迹挂在它上面**。一个 4.6 rad/s 的假初速度，MPC 要花半个窗口
去刹，中点就偏出 35 度。

落到第 0 列的概率不低：同一批参考里切板台阶中位 5.55 度（最小 4.68），远大于
正常逐点变化的 0.13 度（p99 0.41），可以干净地分开；切板平均每 28.5 个采样点
一次，中心差分吃 3 个点，所以**约 7% 的帧**第 0 列的差分会跨到切板上。50 fps
下就是每秒三四次。

本项目的兜底闸门会把这种解全部挡下（50/50 帧超出参考幅值，退回未整形的射击
角），但那等于在最需要整形的换板帧上放弃整形。**sp 没有这个闸门，解永远采
用。** 所以这条偏离必须留着。

差分规则做成对全窗口统一，而不是只修第 0 列：一个整数比较不花什么代价，而
`q_velocity` 一旦不再是 0，中间列立刻就会开始起作用。

### 3. 线性项里的 Q：`Q + rho` → 原始 `Q`

TinyMPC 在 `tiny_setup` 就把 `work->Q` 存成 `Q + rho*I`，`update_linear_cost`
直接拿它乘 `Xref`。定点处的梯度因此变成 `Q*x - (Q+rho)*xref`，相当于把参考
放大 `(1 + rho/Q)` 倍。

本项目用原始 `Q`：rho 那部分已经由 `-rho*(v - g)` 承担，定点处梯度是
`Q*(x - xref)`，干净地以参考为中心。实测该偏置在 `q=1e3, rho=1` 下为 2.4e-4，
改用原始 Q 后降到 3.6e-13。sp 的 `q=9e6` 下这个偏置约 1e-7、可以忽略，但没有
理由继承。

### 4. Riccati 收敛判据：1e-5 → 1e-13

只在 `setup` 跑一次，收紧不花任何运行时代价。对照稠密精确解，本模型上
1e-5 会留下 7e-5 的相对偏差，1e-13 后降到 3.6e-13。

### 5. 输出取哪个变量：未夹的 `work->u` → 夹过的 `z`

sp 读的是 `yaw_solver_->work->x(0, HALF)` 和 `work->u(0, HALF)`：

- `work->u` 是正向滚动出来的**原始 LQR 输入**，没有投影到 `[-a_max, a_max]`；
- `work->x` 是拿这个未夹输入滚出来的状态。

投影过的 `solution->u`（= `znew`）在 sp 的代码里根本没被读到。也就是说
**sp 下发的 `yaw_acc` 可以超过它自己配的 `max_yaw_acc`**，加速度限幅在那边只
通过罚项间接影响解，不是硬保证。

本项目取 `u_ = z_`（一定可行），再按夹过的输入把状态重滚一遍，保证 `x` 与 `u`
自洽——否则下游拿去当速度/加速度前馈会自相矛盾。

### 6. 线性项更新时机：循环末尾 → 循环开头也补一次

TinyMPC 的主循环是"反向递推 → 正向滚动 → 投影 → 对偶更新 → 更新线性项"，
靠跨帧热启动把上一帧的线性项接上。换了参考之后的第一次迭代用的还是上一帧的
`Xref`，白跑一轮；冷启动时更是拿全零线性项开工。本项目在进循环前先按本帧参考
更新一次。

## 三、结构上本来就不同的几处

这些不是对 MPC 的偏离，是两个项目本来的差别。

| | sp_vision | 本项目 |
| --- | --- | --- |
| 选板 | 最近板（`min dist`），每个采样点独立算 | awakening 式结构锁；窗口内走 `locked_id_` 的局部副本，不写回成员 |
| 延迟 | 一个标量 `delay_time`，按 `|v_yaw|` 分两档 | 五段 `Delay`；`send_to_control` 未标定就禁火 |
| 飞行时间 | 一次性，用最近板距离算 | 弹道 ⇄ 命中时刻迭代到收敛 |
| 火控判据 | `|参考 − MPC解|` @ `HALF+2` < `fire_thresh` | **射击角 vs 云台实测角**，且射击角不经整形 |
| 热启动 | 从不清，跨目标也不清 | `Planner::reset()` 清 |
| 兜底闸门 | 无，解永远采用 | `|整形量| <= 参考幅值`，否则本帧退回射击角 |

火控那条本项目更保守：sp 的判据只说"MPC 追上了参考"，不说"云台追上了 MPC"，
下位机没跟上时它照样开火。本项目比的是实测角，代价是必须先标
`planning.send_to_control_ms`。

## 四、已知还没解决的差距

非换板帧上，射击角本来就平滑（隐含加速度 p90 7.2 rad/s²，3181 帧里只有
10 帧超 50），整形之后反而糙到 p90 41.3、175 帧超 50。逐帧整形量在 ±0.2 度
之间抖，20 ms 帧距下就是 12 rad/s²。

根子在结构上：**每帧独立求解、`x0` 取自参考而不是上一帧发出去的命令**，
MPC 只保证单条解内部平滑，不保证帧与帧之间连续。

**sp 有完全相同的弱点**，但它无条件把 `yaw_vel` / `yaw_acc` 一起发给电控
（`io/gimbal/gimbal.hpp` 的 TX 结构体里三个字段都在），由下位机积分闭环，
位置指令上的抖动被积分器吃掉。本项目的 `command_feedforward` 默认关着、
只发位置，抖动就直接进了云台。

两条路：把 `x0` 锚到上一帧自己发出去的命令状态（从原理上修，但偏离 sp），
或者先把前馈打开、按 sp 的路子让下位机去平滑。
